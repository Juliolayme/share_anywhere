# ADR 0012: Key authenticity for account key versions and device wrapping keys

Status: Accepted (Phase 5A QA round 1, 2026-11-11)

## Context

ADR 0004 and `docs/CLIPBOARD_PROTOCOL.md` §1 let any added device rotate the Account Data Key (ADK) and let a device register its X25519 wrapping key as soon as it was added. Phase 5A QA round 1 (P0-1) showed what that allows: a device that only knows the password signs in, adds itself, and posts `POST /v1/keys/rotate` with an ADK of its own choosing. Every other device accepted any rotation blob it could open, so they would switch to the attacker's key and encrypt new history to it. Device wrapping keys were also registered before the device held the ADK, so honest rotations wrapped new keys to devices that had never been paired. The server could not tell an authorized rotation from a forged one because nothing in a rotation was bound to the key it replaced. A dishonest server could do the same by listing a key of its own as a device.

## Decision

- **A signing key per ADK version.** `sign_seed(v) = HKDF-SHA256(ikm = ADK(v), salt = empty, info = "sa-keyver-sign-v1", L = 32)`; the Ed25519 keypair from that seed (RFC 8032, pure) signs as version v, and its public key is `verify_key(v)`. Only holders of ADK(v) can sign as version v. The server stores `verify_key(v)` for every version (`account_key_versions.verify_key`, migration 0007).
- **Setup** sends `verify_key` (verify_key(1)) and `recovery_anchor = HMAC-SHA256(key = HKDF-SHA256(ikm = recovery_seed, info = "sa-recovery-anchor-v1", L = 32), msg = "sa-anchor-v1|" + b64u(verify_key(1)))`, where `recovery_seed` is the Argon2id output of the recovery phrase. A phrase holder can later authenticate verify_key(1) without trusting the server.
- **Rotation** to v+1 sends `verify_key` (verify_key(v+1)) and `signature`, an Ed25519 signature by version v over `"sa-rotate-v1|" + (v+1) + "|" + b64u(verify_key(v+1)) + "|" + b64u(SHA-256(chain_blob))`. Under the per-account key-row lock the server loads verify_key(v): NULL (legacy) is `409 keys_legacy`; a signature that does not verify is `403 rotation_unauthorized` and nothing is stored; otherwise it stores verify_key(v+1) and the signature with version v+1.
- **Proven device wrapping keys.** `PUT /v1/keys/device` takes `{public_key, key_version, proof}`; `proof` is a signature by version `key_version` over `"sa-devkey-v1|" + <caller device ID, lowercase UUID> + "|" + key_version + "|" + b64u(public_key)`. The server takes the device ID from the access token, requires `1 <= key_version <= current` and a stored verify key, and refuses anything else with `403 device_key_unproven`. A device can therefore register only after it holds the ADK (setup, pairing, or recovery). `GET /v1/keys` returns `key_version` and `proof` with each device key so other devices can check it, and rotation's `devices_changed` keeps applying only to devices with a registered (now proven) key. A pairing wrap is accepted only when `sender_public_key` is the caller's registered key.
- **Version list.** `GET /v1/keys/chain` adds `versions: [{key_version, verify_key, signature}]` for 1..current; `GET /v1/keys/recovery` adds `recovery_anchor`.
- **Clients verify** (Web in this round, Android and iOS when they build accounts): rotation pickup requires that the chain link of the candidate ADK(v+1) opens to the ADK(v) they hold and that the candidate derives `versions[v+1].verify_key`; rotating wraps only to devices whose proof verifies with a verify key derived from the rotator's own ADK copy; recovery checks the anchor, every signature from 2 to v, and that the recovered ADK derives `versions[v].verify_key`; pairing receive checks the received ADK against `versions[v].verify_key` and the signature chain.
- **Vectors.** The byte layouts are pinned by the `key_authenticity` section of `shared/protocol/schemas/clipboard-vectors.json`, generated by Go (`backend/internal/auth/keyauth_test.go`, which also re-verifies it) and checked by the Web vectors test.
- **Legacy data.** Migration 0007 adds the columns as NULLable and deletes every existing `device_keys` row (they carry no proof; devices register again once they hold the ADK). Accounts set up before it have no verify keys: they cannot rotate or register (`409 keys_legacy`) and their recovery cannot be verified. This is pre-release development data; no migration path is provided.

## Consequences

- A password-only device (or anyone else without ADK(v)) cannot plant a key, cannot get a new ADK wrapped to it, and is visible in the Devices list; it can still do what the account session allows without keys (revoke devices, change the password, tombstone history), recorded in `docs/SECURITY_MODEL.md` §7.
- A dishonest server cannot forge rotations or device proofs without an ADK, and recovery is anchored to the phrase. Pairing receive is not anchored: the server relays the pairing and can present a fabricated ADK and version list to a brand-new device. That limitation is documented in `docs/SECURITY_MODEL.md` §7; closing it needs an out-of-band confirmation (backlog).
- Rotation and registration now cost one Ed25519 verification on the server and one signature on the client; signing keys are derived on demand and never stored.
- A leaked ADK(v) lets its holder sign as version v; rotation after revoking a device remains the remedy, as before.
- Extends ADR 0004 (the bootstrap and "revoking a device rotates the ADK" are unchanged); it adds how rotations and device wrapping keys are authorized.
