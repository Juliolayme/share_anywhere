# ADR 0014: Current-version key proofs, rotation owed after departures, and pairing anchored on held keys

Status: Accepted (Phase 5A QA round 2, 2026-11-11). Amends ADR 0012. Amended by ADR 0015.

## Context

Phase 5A QA round 2 found three gaps in the key authenticity rules of ADR 0012.

- **P1-A (stale proofs).** ADR 0012 accepted a device-key proof by any version from 1 to the current one, and rotation demanded a blob for every other added device with a registered key. A device that was revoked after holding ADK(1), and that keeps ADK(1) and knows the password, could sign in on a new device, add it, and register a key with a proof by version 1. The owner's next rotation then had to wrap the new ADK to it. The reviewer's live sequence: A rotates to 2 after revoking laptop L; thief X registers with L's version-1 proof (`204`); A's rotation to 3 without X is refused (`409 devices_changed`, `missing: [X]`); with X it succeeds and X receives version 3.
- **P2-1 (rotation only after a revoke from Devices).** Clients rotated only right after revoking a device from the Devices screen. Devices that left the account any other way (sign-out, password reset, password change, identity reset, refresh-secret reuse, expiry) kept the current ADK and no rotation followed.
- **P1-B (pairing receive trusted the server even on devices that held keys).** A device that already held ADK versions accepted a pairing result checked only against the server's version list, and a key check that saw `key_version 0` wiped the local keys.

## Decision

Contract wording (quoted from the frozen Phase 5A QA round 2 contract, sections D, E, F):

- **D.1 Proofs by the current version only.** `PUT /v1/keys/device`: "`key_version` must equal the account's current key_version (else `409 key_version_conflict`, nothing stored)." The proof is verified as before (`403 device_key_unproven` when it does not verify or the account has no ADK yet).
- **D.2 Rotation wraps exactly to devices proven at the current version.** `POST /v1/keys/rotate` from v to v+1: "the set of devices that must receive a blob is other added devices whose registered proof has `key_version == v`." A blob for any other device (no registered key, a proof older than v, or not an added device of the account) is refused like a missing one: `409 devices_changed` with `{missing: [...], unexpected: [...]}`, both arrays always present, nothing stored. The caller may still include a safety copy for itself. This replaces the `400 invalid_request` with `unexpected` of ADR 0012. Devices with an older proof get nothing and must pair again or use the recovery phrase.
- **D.3, D.4 Clients.** A rotating client wraps only to devices whose proof is by its own current version and verifies with the verify key derived from its own copy of that ADK, never to the device it just revoked (skipped reasons `no_key`, `unproven`, `stale`, `excluded`). A device whose newest held version is greater than the version of its own registration registers again with a proof by its newest version (after setup, pairing, recovery, pending pickup, chain import), refreshing and retrying once on `409 key_version_conflict`.
- **E Rotation owed after any departure.** `account_keys.rotation_due boolean NOT NULL DEFAULT false` (migration 0008). Every way a device leaves an account goes through one server function (`detach`, `backend/internal/auth/sessions.go`; the single path ADR 0010 describes), which sets `rotation_due` in the same transaction when a leaving device had a registered wrapping key (revoke from Devices, sign-out, password reset, password change for other devices, refresh-secret reuse, expiry sweep, identity reset). A successful rotation clears it. `GET /v1/keys` adds `rotation_due`. A ready client that sees it rotates automatically on the same path as after a revoke, retrying once after `409 key_version_conflict` or `devices_changed`, and retries on the next key check after a failure.
- **F Pairing anchored on held keys; no silent wipe (client side).** When the receiving device already holds ADK versions (newest k), `acceptPairing` requires the received version v ≥ k, checks every held version against the server's verify keys (constant time), verifies signatures only from k upward, and when v > k walks the chain from the received ADK(v) down to k and requires it to equal the held ADK(k); any failure stores nothing. A key check that reports version 0 (or lower than held) for the same account no longer wipes keys: the key state becomes `rejected` and the keys are kept. A refusal of this device's own rotation or registration (`rotation_unauthorized`, `device_key_unproven`, `key_version_conflict`) gets its own state and message.

## Consequences

- A former device that kept older ADK versions and knows the password can still sign in and add a device, but cannot register a key and never receives a later version; it can still decrypt history under the versions it held (`docs/SECURITY_MODEL.md` §7).
- After every rotation each device must register again with a proof by the new version once it picks the version up. A device that has not done so when the next rotation happens is left out and must pair again or use the recovery phrase; with clients re-proving on every key check this needs the device to stay offline across two rotations.
- Any departure of a device that held a key now leads to a rotation by the next ready device to check keys, not only a revoke from the Devices screen. A dishonest server can hide `rotation_due` (denial of service, not disclosure).
- The pairing-receive limitation of ADR 0012 ("not anchored") now applies only to a device holding no ADK (a brand-new device); a device that holds keys anchors pairing on them.
- Docs also record that in-origin script on the Web can read raw ADK bytes while it runs (the client unwraps them to wrap pairing and rotation blobs); non-extractability protects the device KEK, the subkeys, and the device private key (`docs/SECURITY_MODEL.md` §7, `docs/CLIPBOARD_PROTOCOL.md` §1.11).
- Amends ADR 0012 (the "`1 <= key_version <= current`" rule, the rotation blob rule and its `400` answer, and the scope of the pairing-receive limitation in its Consequences); ADR 0004 and the rest of ADR 0012 are unchanged.
