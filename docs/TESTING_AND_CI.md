# Testing and CI strategy

Goal: every claim in a phase report is backed by an automated run on GitHub Actions, using emulated platforms where real devices are unavailable. This document defines the workflows, the emulation approach per platform, and what each phase must add.

---

## 1. Platform emulation summary

| Platform | How it is emulated in CI | What it proves | What it cannot prove |
|---|---|---|---|
| Web desktop (Chrome, Firefox, Safari engine) | Playwright projects `chromium-desktop`, `firefox-desktop`, `webkit-desktop` on `ubuntu-latest` | Routing, UI states, WebRTC Web↔Web, clipboard permission paths, File System Access / OPFS branches | Real Safari UI prompts, OS-level clipboard behavior |
| Web on Android (Chrome) | Playwright `android-chrome` project with `devices['Pixel 7']` (Chromium engine, mobile viewport, touch, UA) | Mobile layout, touch targets, join-page flow, QR/code usability | Real Android Chrome download manager, App Links |
| Web on iOS (Safari) | Playwright `ios-safari` project with `devices['iPhone 14']` (WebKit engine, iOS UA, viewport, touch) | Mobile Safari layout, WebKit API availability (no File System Access API, OPFS behavior), clipboard gesture requirement | Real iOS tab suspension, storage quota prompts, real Safari permission dialogs. **Mark these "verified on WebKit emulation, not on a real iOS device".** |
| iOS app | `macos-15` runner, Xcode 16.x, `xcodebuild test -destination 'platform=iOS Simulator,name=iPhone 15'` with XCTest unit tests and XCUITest; backend runs **natively** on the runner (Homebrew `postgresql@16` + `coturn`, Go binary) because macOS GitHub runners have no Docker; Playwright peer runs on the same runner for interop | SwiftUI screens, navigation, document picker flows with seeded files, foreground clipboard capture, `UIPasteControl` path, guest-first launch and guest transfers, optional sign-in and session API integration, iOS ↔ Web interop | Real device background suspension timing, Universal Links, camera QR scanning (simulator has no camera; use code entry), App Review outcomes. **Mark these "verified on iOS Simulator, not on a real device".** |
| Android app | `reactivecircus/android-emulator-runner` with KVM on `ubuntu-latest`, API 34 (required) and API 35, 29 (nightly). Instrumentation tests with Compose testing + Espresso. Backend reachable from emulator at `10.0.2.2`. | Compose screens, navigation, SAF flows with test documents, clipboard foreground capture, guest-first launch and guest transfers, optional sign-in and session API integration, Android↔Web interop via a Playwright receiver running on the same runner | Battery/thermal behavior, OEM clipboard quirks, real App Links verification, Play policy review |
| Backend | Go tests with a PostgreSQL 16 service container; coturn service container for TURN tests | API contracts, access levels (guest vs account), rate limits with an injected clock, atomic max-5, state machines, TTLs, cursor ordering, TURN credential issuing | Production network conditions |
| Large files | Sparse fixtures generated by `scripts/gen-fixture.sh` (`truncate` + random blocks at known offsets). PR: 256 MB. Nightly: 2 GB. 20 GB: manual runbook only. | Streaming, hashing, resume bitmaps at scale, memory ceilings | 20 GB on consumer networks |

Rule: a phase report may only call a platform behavior "tested" if a workflow in this repo executed it. Everything else is "untested" or "emulated only".

## 2. Workflows

### 2.1 `ci.yml` — on every pull request and push to `main`

Path filtering with `dorny/paths-filter` so Android changes do not run Web e2e and vice versa. Shared changes (`shared/protocol/**`, `docker-compose.yml`, `.github/**`) run everything.

Jobs:

| Job | Trigger paths | Steps | Required from phase |
|---|---|---|---|
| `protocol` | `shared/**` | Validate `openapi.yaml` (Redocly or `openapi-spec-validator`), validate `websocket-events.json` against its JSON Schema, check generated TS/Go/Kotlin clients are up to date (`git diff --exit-code` after regeneration) | 1 |
| `backend` | `backend/**`, `shared/**` | `go vet`, `golangci-lint`, `go test -race -cover ./...` with services: `postgres:16`, `coturn/coturn`; migrations run against the service DB | 1 |
| `web` | `web/**`, `shared/**` | `pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm typecheck`, `pnpm test` (Vitest + Testing Library), `pnpm build`, bundle-size check | 1 |
| `e2e-web` | `web/**`, `backend/**`, `shared/**` | Build backend image, `docker compose -f docker-compose.ci.yml up -d` (postgres, backend, coturn, caddy with self-signed cert), `pnpm exec playwright install --with-deps`, run Playwright with matrix `project: [chromium-desktop, firefox-desktop, webkit-desktop, android-chrome, ios-safari]` with `--trace retain-on-failure`; the report and traces are uploaded on every run, so a test that passed only on retry can still be diagnosed | 1 (smoke), full from 2 |
| `android` | `android/**`, `shared/**`, `scripts/**`, `design/**`, `.editorconfig` | JDK 17 via `actions/setup-java`, `gradle/actions/wrapper-validation` (wrapper jar checksum), `gradle/actions/setup-gradle` (cache), then in `android/`: `./gradlew assembleDebug testDebugUnitTest lintDebug ktlintCheck assembleDebugAndroidTest`; uploads the debug APK and the test and lint reports. **Built in Phase 6 (milestone 6.1).** Generated Android sources (tokens, strings, API models) are checked by the `protocol` job, whose path filter includes them | 6 |
| `android-emulator` | `android/**`, `backend/**`, `shared/**` (plus `scripts/**`, `design/**`) | Calls the reusable `android-emulator.yml` with API 34, `google_apis`, `x86_64`, `connectedDebugAndroidTest`: enables KVM, starts `docker-compose.ci.yml`, boots the emulator with `reactivecircus/android-emulator-runner@v2.33.0` (AVD snapshot cached), runs `./gradlew connectedDebugAndroidTest -Pbackend=http://10.0.2.2:8080` with the Android Test Orchestrator (`clearPackageData`, so each test is a fresh install), uploads instrumentation reports. **Built in Phase 6 (milestone 6.1).** | 6 |
| `ios` | `ios/**`, `shared/**` | `macos-15`, `xcodegen generate`, SwiftLint, SwiftFormat `--lint`, `xcodebuild build-for-testing` + `test-without-building` for the `ShareAnywhereCore` package unit tests (JVM-equivalent: no simulator UI), upload `.xcresult` | 7 |
| `ios-simulator` | `ios/**`, `backend/**`, `shared/**` | `macos-15`, start Homebrew Postgres + coturn, run Go backend natively with migrations, boot `iPhone 15` simulator, `xcodebuild test` for XCUITest with `BACKEND_URL=http://127.0.0.1:8080`, upload screenshots and `.xcresult` | 7 |
| `security` | all | `gitleaks`, `govulncheck`, `pnpm audit --audit-level=high`, `actions/dependency-review-action` on PRs, Trivy on the backend image | 0 |
| `docs` | `docs/**`, `*.md` | markdownlint, link check | 0 |

Branch protection: `protocol`, `backend`, `web`, `e2e-web`, `security` required from Phase 1; `android`, `android-emulator` required from Phase 6; `ios`, `ios-simulator` required from Phase 7. Since Phase 6 milestone 6.1 the `android` and `android-emulator` jobs run on every matching change but are not required yet; they become required checks when the Phase 6 exit gate is met.

Cost note: macOS minutes are billed at 10× Linux minutes. `ios` and `ios-simulator` run only on `ios/**`, `backend/**`, `shared/**` changes, cache DerivedData and SPM checkouts, and the full simulator matrix lives in nightly.

### 2.2 `nightly.yml` — scheduled daily

- `large-file` (**built in Phase 3**, `web/e2e/nightly/large-file.spec.ts`): Playwright `chromium-desktop` Web↔Web transfer of a 2 GB sparse fixture with a receiver reload after a quarter has arrived (resume test). Asserts zero duplicate blocks, the downloaded file's SHA-256, and a peak JS heap (`performance.memory.usedJSHeapSize`) under 512 MiB on both sides.
- `turn-forced`: Web↔Web with `iceTransportPolicy: 'relay'` through the coturn container; asserts selected candidate pair is `relay` on both UDP and TCP/TLS configurations.
- `five-receivers` (**built in Phase 4**, `web/e2e/nightly/five-receivers.spec.ts`, `E2E_FIVE=1`): one guest sender and five guest receivers: three Chromium, one stock Firefox, one WebKit (persistent context). One receiver is slowed with the test-build receiver write delay, because CDP network conditions do not throttle WebRTC data channels (the phase file's "throttled via CDP" is met this way, in every engine). Asserts that a sixth join is refused, that the other four complete while the slow one is still going (the sender keeps the screen on), and that the slow one then completes; SHA-256 of every download.
- `android-matrix`: emulator API 29, 34, 35; same instrumentation suite; API 35 additionally runs the `dataSync` foreground-service time-limit simulation (`adb shell cmd activity fgs-timeout` where available, otherwise an injected clock).
- `android-web-interop`: all participants are **guests**. Emulator (Android sender via instrumentation test that creates a session and returns the code) + Playwright `chromium-desktop` receiver on the same runner; asserts file hash. Then the reverse direction.
- `clipboard-cross-client`: Playwright Web, signed in with a device added, creates an encrypted clipboard event; Android instrumentation test on the emulator receives, decrypts with a paired key, and verifies plaintext; backend DB dump asserts no plaintext present. Same assertion with the iOS Simulator on the macOS runner.
- `ios-matrix`: iPhone SE (3rd gen) and iPhone 15 Pro Max on the latest runtime, plus iPhone 15 on the oldest iOS 16 runtime the runner offers; XCUITest suite with Dynamic Type `accessibilityExtraExtraExtraLarge` variant.
- `ios-web-interop`: all participants are **guests**. iOS Simulator sender (XCUITest creates a session and writes the code to a shared file) + Playwright `chromium-desktop` receiver on the same macOS runner; asserts hash; then the reverse direction.
- `ios-background-suspend`: XCUITest sends the app to background mid-transfer (`XCUIDevice.shared.press(.home)`), waits past the background window, returns, and asserts resume from bitmap with zero re-sent verified blocks.
- `android-ios-interop`: not possible on one runner (Linux emulator vs macOS simulator); runs as two half-tests against a shared ephemeral backend deployed by the workflow on a Linux job and reached over the runner's public egress through Caddy with a self-signed cert pinned in the apps' debug builds. Treat as best-effort and allow failure without blocking until Phase 9.

### 2.3 `ios-simulator.yml` — reusable workflow

Inputs: `device`, `runtime`, `scheme`, `test-plan`. Starts native Postgres and coturn via Homebrew services, runs the Go backend, boots and pre-warms the simulator (`xcrun simctl boot`, `simctl bootstatus -b`), runs `xcodebuild test`, uploads `.xcresult` and screenshots.

### 2.4 `android-emulator.yml` — reusable workflow

Shared by `ci.yml` and `nightly.yml`. Inputs: `api-level`, `target`, `arch`, `gradle-task`. Caches the AVD snapshot keyed by API level to cut boot time.

**As built (Phase 6, milestone 6.1):** `.github/workflows/android-emulator.yml` (`workflow_call`). Steps: KVM udev rule, JDK 17, wrapper validation, `setup-gradle`, `docker compose -f docker-compose.ci.yml up -d --build --wait` (the e2e-web stack; Caddy on host port 8080, which the emulator reaches as `10.0.2.2:8080`), a host health check, `assembleDebug assembleDebugAndroidTest` before the emulator boots, an AVD cache keyed by API level, target and ABI (`v1` suffix to invalidate), then `reactivecircus/android-emulator-runner@v2.33.0` (`-no-window -gpu swiftshader_indirect -no-boot-anim`, animations disabled) running `./gradlew <gradle-task> -Pbackend=http://10.0.2.2:8080` in `android/`. Reports (`app/build/reports/androidTests`, `app/build/outputs/androidTest-results`) are uploaded on every run; compose logs on failure. `ci.yml` calls it with API 34. Nightly API 29/35 matrix and interop jobs are later milestones.

## 2b. Identity defaults in tests

- **Guest is the default identity in every test.** Transfer, pairing, history, settings, and onboarding specs never sign in. A Transfer spec that needs an account is a bug in the spec or in the product.
- Only specs under `account/` and `clipboard/` (Web), `AccountTests` and `ClipboardTests` (Android, iOS) create accounts, and each of them also asserts the guest variant of the screen it covers.
- Each client has a fixture that creates a fresh anonymous identity per test context, so guest tests never share device IDs.
- Rate-limit tests use test configuration (low limits) and an injected clock; they never sleep, and production limits are never disabled to make other tests pass. Normal e2e runs use per-test IPs where possible (distinct `X-Forwarded-For` values from the trusted CI proxy) so the suite does not trip its own limits.

## 3. Playwright configuration contract

`web/playwright.config.ts` defines:

```ts
projects: [
  { name: 'chromium-desktop', use: { ...devices['Desktop Chrome'], permissions: ['clipboard-read', 'clipboard-write'] } },
  { name: 'firefox-desktop',  use: { ...devices['Desktop Firefox'] } },
  { name: 'webkit-desktop',   use: { ...devices['Desktop Safari'] } },
  { name: 'android-chrome',   use: { ...devices['Pixel 7'] } },
  { name: 'ios-safari',       use: { ...devices['iPhone 14'] } },
]
```

Conventions:

- Clipboard permissions can only be granted in Chromium. Firefox and WebKit projects therefore exercise the **permission-denied / gesture-required** paths, which is exactly the behavior the product must handle. Tests use `test.skip(browserName !== 'chromium')` only for the granted path and must have a mirrored denied-path test.
- WebRTC tests run the sender in a Chromium browser launched inside the test and the receiver in the project's browser (two browser processes on one runner). Host candidates are hidden behind mDNS names by default, and CI has no mDNS resolver, so Chromium launches with `--disable-features=WebRtcHideLocalIpsWithMdns` and Firefox with `media.peerconnection.ice.obfuscate_host_addresses = false` (`web/playwright.config.ts`, `chromiumWebRtc`). This is browser configuration for the test machine, not product behavior; real users keep the browser defaults. ICE servers still come from `POST /v1/turn/credentials` (TURN plus the derived `stun:` URI).
- **Firefox:** Playwright's patched Firefox build never gathers ICE candidates (ICE fails before any candidate, with or without STUN/TURN; seen locally and in CI run 42827720718). The `firefox-desktop` project therefore drives a stock Firefox over WebDriver BiDi (`channel: 'moz-firefox'`) when `E2E_FIREFOX_BIN` points at it; CI downloads a pinned, checksum-verified Firefox release for that job (`ci.yml`). The sender's Chromium launch passes its own channel and executable so the Firefox project's options do not leak into it. Codes are typed key by key (`pressSequentially`), which behaves the same in every driver. The Firefox project also sets `network.proxy.type = 0`: a system proxy picked up from the environment (this development container has one) makes Firefox stop gathering ICE candidates on every page after the first, a reload included, while the first page still connects. Reproduced with a bare `RTCPeerConnection` outside the app; gone with the pref or without the proxy variables. CI showed the same symptom after a receiver reload in about half of the runs (42853814739, 42863480743, 42871975278, 42879038016 attempt 2, 42886311449). **Cause, from the per-browser Firefox ICE logs:** a page without a camera or microphone permission makes Firefox gather only its default-route address (confirmed: one host candidate without the permission, every interface with it). To find that address it runs a UDP route probe. In the reloaded page that probe fails on the runner (`PR_Connect failed: -5980`, network unreachable, for both families), so `failed to find default addresses` → `ICE FAILED: Couldn't gather ICE candidates` on every dial of that document. The first page's probe succeeds. It is not the ICE server address: it recurred after the stacks moved from `localhost` to `127.0.0.1` (kept, since `localhost` also produced `ice-error 701` when it resolved to `::1`). Fix in the test stack: Firefox receiver contexts are granted camera and microphone (`receiverPage`), so Firefox gathers every interface and skips the probe; this is test-machine configuration like Chromium's mDNS flag. Why the reloaded page's probe fails on a runner where the first page's probe works is not known. Real Firefox users always run in default-route mode, so a Firefox receiver that reloads mid-transfer may hit the same failure, and so may one on a network without a default route (a LAN without internet); both untested, recorded as limitations in the Phase 3 report. Because every Firefox receiver in the suite has the permission, no spec currently exercises Firefox's default-route mode (backlog). It is not the receiver closing its peer connection on `pagehide` (removed; it recurred without it). For diagnosis the Firefox CI job sets `MOZ_LOG=timestamp,jsep:4,signaling:4,mtransport:3,nicer:4` (one file per receiver browser) with `MOZ_LOG_FILE` under `web/moz-log/` (uploaded with the results), test builds keep the receiver's diagnostics across a reload (`prev:` lines), and each dial records its ICE server URLs, whether the offer was set and the gathering state. Each Firefox receiver also gets its own freshly launched browser (`receiverPage`, closed by `closeReceiverBrowsers()`), so no state carries over from earlier specs.
- **Transfer specs** (`web/e2e/transfer/`, `web/e2e/mobile/transfer.spec.ts`) run against a web image built with `VITE_TEST_HOOKS=true` (`docker-compose.ci.yml`). The test build exposes `window.__saTest` with each controller's engine counters (blocks received, duplicates, NACKs, resumed bytes) and three sender hooks: pace (delay before each block, so a spec can pause, reload, or disconnect mid-transfer), corrupt (flip a byte in the next block after hashing), and drop (close every peer connection and ignore offers for a while); plus one receiver hook, pace (delay before each block write: a slow receiver in any engine). `web/e2e/transfer/multi.spec.ts` (Phase 4) runs two receivers per test on the desktop projects: one slowed (the fast one finishes first and the sender holds the screen until the last ends), Remove and Block mid-transfer (the other completes; a blocked device cannot rejoin), Close session (every receiver sees it end), a receiver joining after the result (the dashboard returns, then New transfer closes the session), and a second tab of the sender on the same session (it leaves the transfer to the tab with the files, shows the other-tab notice, offers no Pause on its dashboard while Remove stays, and does not overwrite History). Production images do not expose them: without `VITE_TEST_HOOKS` there is no `window.__saTest`, so the pace, corrupt and drop fields in the controllers stay at their defaults and cannot be reached (the code itself is still in the bundle).
- Playwright's WebKit contexts are ephemeral, which behaves like Safari private browsing: no Origin Private File System. WebKit receivers in transfer specs therefore run in a persistent context (`receiverPage()`), like a normal Safari window; one spec deliberately uses an ephemeral WebKit context to cover the in-memory path for private windows.
- Fixtures come from `scripts/gen-fixture.sh` through the `fixture()` helper (generated once per machine under `E2E_FIXTURE_DIR`, never committed). PR runs use 8, 16 and 64 MB; the nightly `large-file` job uses 2 GB (`E2E_LARGE=1`).
- Forced relay tests set `window.__SA_TEST_ICE_POLICY = 'relay'` via `addInitScript`, which the transfer engine reads only in builds with `VITE_TEST_HOOKS=true`.
- Large-file tests read fixtures via `page.setInputFiles` with the sparse file path; receiving uses OPFS in all engines, plus the Save to a folder path in Chromium, where an init script replaces `showDirectoryPicker` with one that returns a real directory handle (an OPFS folder), since the native picker cannot be driven.
- Every e2e test asserts on accessible roles/names, not CSS selectors.
- Guest-first smoke spec runs first in every project: fresh context → Welcome → Start sharing → Transfer home, asserting no element with role `heading` named "Sign in" or "Create account" and no password field appears on the path (since Phase 5A Welcome offers only the optional "Already have an account? Sign in" link), and a join link opened in a fresh context lands on the join preview without Welcome.
- **Keep-screen-on specs** stub `navigator.wakeLock` through `addInitScript` with a recorder that supports three modes: `granted` (returns a sentinel whose `release()` is counted and which fires `release` when the test hides the page), `refused` (rejects with `NotAllowedError`), and `unsupported` (property absent). Specs assert the screen-on pill label and state, that a request happens only in active states, that `release()` is called on completion, pause, cancel, removal, close, and expiry, that a new request follows `visibilitychange` to visible while still active, and that nothing is requested with the setting off. Headless browsers may refuse a real wake lock, so the real API is exercised only in one informational Chromium run whose outcome is logged, not asserted.
- **Open-join specs** assert that a receiver who enters a valid code or opens a link reaches the receiving state without any sender action, and that the sender sees the join toast and security words.
- **Account specs** (`web/e2e/account/`, Phase 5A) are the only Web specs that create accounts; each test signs up a fresh address (`uniqueEmail()`), so no state is shared. Helpers live next to them (`helpers.ts`: `signUp`, `signIn`, `chooseAndContinue`, `saveRecoveryPhrase`, `finishChecklist`, `addLocalEntry`, `resetLink`, `typeInto`) and reuse `guestPage` / `open` / `closeContexts` from `e2e/pairing/helpers.ts` (`closeContexts` in `afterEach`). Fields are typed with real keystrokes (`typeInto`): under WebDriver BiDi Playwright's `fill` sets the value without input events, so React never sees it. Specs: after-sign-in choices both ways and the Devices list (`choices.spec.ts`); a second context pairing by pasted code, refused codes and a wrong phrase, recovery with the saved phrase, and revoking a device (the key rotates; the revoked browser is a guest again with an empty key store) (`keys.spec.ts`); history sync between two contexts with a tombstone back, the one-time import, and no upload of pre-sign-in history without it (`history-sync.spec.ts`; entries are written into the History IndexedDB as a finished transfer would, the transfer recording itself is covered by `e2e/transfer/`); sign-out keep and clear (new device ID, empty key store) and password reset through `GET /v1/_test/mail/last` (`signout-reset.spec.ts`); a guest receiver that finishes one transfer and signs in from Settings during a second, paced one (`senderHook`), which completes with the same device ID (`signin-during-transfer.spec.ts`); Welcome → Transfer home and Send / Receive / History without any sign-in screen, the optional Welcome link, and `returnTo` validation (`welcome.spec.ts`). Key authenticity and session binding (`authenticity.spec.ts`, QA round 1): a second context that signs in with only the password and adds its browser has no registered device key, and its forged `POST /v1/keys/rotate` and self-proven `PUT /v1/keys/device` are refused (`403 rotation_unauthorized`, `403 device_key_unproven`) while the real device stays ready (the bearer token is read off the app's own requests, since access tokens live in memory only); a not-added session ends when its `sa_acct` browser-session cookie is cleared (reload → Guest), and an added session has no such cookie and stays signed in. QA round 2 (same file): after the owner revokes a laptop that held ADK v1 (the key rotates to v2), a thief who kept v1 and knows the password signs in, adds a browser, and proves a device key with v1: `409 key_version_conflict`, nothing stored; a spare browser that recovered v2 then signs out, the server marks a rotation owed, and the owner's next key check rotates to v3 by itself with no blob for the thief (`rotation_due` back to false). The spec opens the account's current ADK with the recovery phrase in Node (`keys-node.ts`, the app's own crypto modules plus `@noble/hashes` Argon2id) to make the genuine old-version proof. The client-side refusal of a forged rotation blob, unproven and stale devices, forged or tampered recovery data, pairing anchored on held keys (the QA round 2 scratch proofs turned into regressions: `web/src/lib/crypto/anchoring.test.ts`), re-proving, owed rotations, no wipe on a server reporting `key_version 0`, the honest key states (`rejected` vs `refused`), and the QA round 3 regressions (a server-substituted recovery key gets no blob and no rotation is sent; a device left behind shows Pair; no second rotation after another device made the owed one; remembered exclusions; key checks on visibility and the 30 s tick; history upload retry after `409 key_version_conflict`; verified chain import) are Vitest (`web/src/lib/crypto/authenticity.test.ts`, `anchoring.test.ts`, `authenticity-vectors.test.ts`, `web/src/features/account/keyFlow.test.ts`, `AccountContext.test.tsx`, `accountUi.test.tsx`, `sync/historySync.test.ts`); the backend side (setup without or with a bad recovery key signature, `recovery.signature` in `GET /v1/keys`, history entries under an older key) is `backend/internal/auth/keys_test.go` and `history_test.go`. Playwright's WebKit (Linux) showed two engine quirks that the key library now handles (`docs/CLIPBOARD_PROTOCOL.md` §1, Web local storage): a WebCrypto X25519 key stored in IndexedDB reads back as `undefined`, and X25519 scalars whose first byte is zero fail to import or generate (about 1 in 32). Camera QR scanning (`BarcodeDetector`) is not exercised: no project has a camera, and the paste path covers the same server flow.
- **Pairing specs** (`web/e2e/pairing/`) always run the sender in a Chromium browser launched inside the test (each `e2e-web` job installs Chromium plus its own browser) and the receiver in the project's browser. Because the clock and protected-mode hooks are global to the test backend, Playwright runs with one worker.
- Pairing specs navigate with the `open()` helper (`web/e2e/pairing/helpers.ts`). CI traces (runs 42802588370 and 42805131808) show Playwright's Firefox driver sometimes reporting no lifecycle event at all, not even the commit, for a fresh page's first navigation, although the document, assets and API calls complete. The helper bounds the commit wait at 10 s, issues the navigation once more on timeout and adds a `navigation-retry` annotation to the test, then asserts the target URL and the app shell (`#main`). A failed second attempt or a wrong URL fails the test. This is a mitigation, not a root-cause fix: the retry hides the stall from Playwright's flaky count, so the backlog target is zero flaky tests **and** zero `navigation-retry` annotations (visible as junit properties) over several CI runs. A retried `/j/<token>` resolves the link twice, which counts two failed lookups for an unknown or expired link.
- **Mobile legibility (Phase 2):** asserted with sizes and overflow (QR ≥ 160 px, code ≥ 28 px, no horizontal scroll) instead of visual snapshots. Since Phase 3, `web/e2e/mobile/snapshots.spec.ts` also compares visual baselines per mobile project. The baselines are generated on the CI runner by `nightly.yml` `mobile-snapshots` (fonts must match CI), downloaded from its artifact, and committed under `snapshots.spec.ts-snapshots/`; values that change on every run (codes, QR, names, security words) are masked. Local runs on other machines may differ by anti-aliasing.
- **Join-window specs** never wait 10 real minutes: the backend runs with an injectable clock in CI and exposes a test-only endpoint (compiled only into test builds) to advance it; specs assert the 10:00 countdown, the "Code expired — Create new code" state, renewal, and that joined receivers keep transferring.
- **Clipboard specs** (`web/e2e/clipboard/`, Phase 5B) create their own accounts like the account specs and reuse their helpers (`signUp`, `signIn`, `chooseAndContinue`, `saveRecoveryPhrase`, `typeInto`) and `guestPage` / `open` / `trackContext` / `closeContexts` (`afterEach`). `helpers.ts` adds `instrumentClipboard` (an init script that counts `Clipboard.prototype.readText` / `writeText` / `read` / `write`, `Permissions.prototype.query`, and `copy` / `paste` listeners on the document or window into `window.__cb`, before any app script runs; with `denyRead` it makes `readText` reject with `NotAllowedError`), `clipboardPage` (Welcome seen, instrumented, clipboard permissions granted on request), `signUpFromClipboard` / `signInFromClipboard` / `goToClipboard` (the account flow started from the Clipboard intro, returning to it), `pairByCode`, `syncByPaste` (Sync Clipboard → paste fallback), `refocus` (dispatches `focus` and `visibilitychange`), and IndexedDB readers for held ADK versions, clipboard records, and cached key versions. Specs: `guest.spec.ts` (every project: CB-1 intro, zero clipboard calls of any kind while a guest, including after navigating, Sign in from the intro returns to Clipboard as CB-2 with still zero calls; CB-6 disabled with Sign in); `granted.spec.ts` (`chromium-desktop` only, the one project where Playwright can grant `clipboard-read` / `clipboard-write`: status `auto`; automatic capture off → manual capture; Sync reads a value the test wrote, the request carries no plaintext; a second context signs in from Clipboard, pairs by pasted code, and shows the item; a new item reaches it live over WebSocket with New; Copy writes it to the clipboard (verified by reading it back after overwriting); item drawer; automatic capture on reads once on focus, off does not read; search and delete everywhere); `denied.spec.ts` (`firefox-desktop`, `webkit-desktop`, `android-chrome`, `ios-safari`: real capability detection gives `unsupported` on Firefox and WebKit and `besteffort` or `denied` on headless mobile Chromium (the permission is not granted to the context); focus and visibility never read (no prompt loop); Sync reads exactly once in the click and the refusal (`denyRead`, because Playwright cannot click Firefox's or Safari's Paste button or answer Chrome's prompt) opens the paste fallback, which syncs; sensitive text is skipped with the disclaimer and **Sync anyway** sends it; Copy succeeds or falls back with a message); `insecure.spec.ts` (`chromium-desktop` only: a Chromium launched with `--host-resolver-rules=MAP sa-insecure.test 127.0.0.1 --no-proxy-server` opens `http://sa-insecure.test:8080`, which is not a secure context (unlike `http://localhost`); Clipboard shows "HTTPS required" and makes no call; the Compose CI edge proxy answers any host name, and no backend origin or cookie setting is needed because the page never gets a device identity there); `revoke.spec.ts` (every project: a device recovered with the phrase reads an item, is revoked, the next item is cached under key version 2, and the revoked browser is a guest with no ADK and no clipboard records). Vitest covers the rest: item encryption round trip, nonce uniqueness over 10,000 items, AAD tamper (event_id or key_version changed, a server swapping or relabelling rows shows them locked), the sensitive heuristics, the offline queue (IndexedDB, survives a reload, sent once, idempotent retry), `409 key_version_conflict` re-encrypt and retry once, `409 clipboard_paused`, `413` drop, cursor and tombstone handling, retention and the 100-item cap, status derivation, the runtime's focus / visibility / in-page copy rules, CB-4 flows, and the Phase 5B QA round 1 regressions: lowercase canonical item ids on the wire and in the AAD for clipboard events and history entries (`web/src/lib/crypto/item.test.ts`, `engine.test.ts`), no ghost row when a create's response is lost and another device deletes the event (tombstone pulled while queued, and a retry acknowledged before the tombstone), a wipe in another tab (a second connection to the same IndexedDB) refusing every later write of a running engine (`store.test.ts`, `engine.test.ts`), in-page copies only while the status panel says `auto` or `besteffort` with the switch on (`status.test.ts`, `runtime.test.ts`), the queued toast's cause (offline, `5xx`, `429`, paused), and the offline and error states of a first load with nothing cached (`ClipboardHome.test.tsx`), the guest path making no clipboard call and never loading the runtime, and a source-structure guard (only `capture.ts` touches the clipboard, only the runtime imports it, only `ClipboardProvider` loads the runtime, dynamically) (`web/src/features/clipboard/*.test.ts(x)`).
- Mobile projects run a dedicated `mobile/` spec folder covering join page, code entry and QR display legibility, plus a visual snapshot per screen at the project's viewport; clipboard manual sync on mobile is covered by `clipboard/denied.spec.ts`, which runs in both mobile projects.

## 4. Backend test conventions

- Unit tests next to code. Integration tests tagged `//go:build integration`, run in CI with `DATABASE_URL` pointing at the service container.
- Concurrency tests for max-5: spawn 20 goroutines joining one session; exactly 5 succeed; the rest receive `409 session_full`. Run with `-race`.
- Cursor ordering test: 50 parallel inserts for one user; reading with cursors never skips or duplicates an event.
- Access-level tests generated from `openapi.yaml`: for every operation, call it with no token, an expired token, a guest token, a signed-in not-added token, a signed-in added token, a non-participant device, a `REQUESTED` receiver, a removed receiver, a blocked device, and a revoked device; assert the result matches the operation's `x-sa-access` level (`401`, `403 account_required`, `403 device_not_added`, `404`, or success).
- Token tests: EdDSA only, unknown `kid`, tampered claims, expired; refresh rotation and reuse detection revoking the device.
- Rate-limit tests with test config and an injected clock for: anonymous device creation and proof-of-work threshold, session creation per device and per IP, concurrent open sessions, code lookup with lockout (one IP, many devices), join requests (requests count toward the five receiver slots), TURN credential issue limits, WebSocket connection caps, sign-in/sign-up/reset. Each asserts `429` with `Retry-After` and that the limit resets after the window.
- Trusted-proxy test: `X-Forwarded-For` from an untrusted peer is ignored.
- Join-mode tests: open join returns `JOINED` for code and link; `require_approval` returns `REQUESTED`; toggling affects only later joins; protected mode, driven by the failed-lookup counter with an injected clock, forces `REQUESTED` for code joins only and expires after 30 minutes; Block covers device ID and IP /64; 10-minute join window for code, link, and QR (admit at 9:59, refuse at 10:00, join ticket capped at window end, ends on fifth receiver and on Stop accepting, Create new code invalidates the old code and link and restarts the window, unavailable while full, joined receivers unaffected by expiry).
- Lifetime tests with an injected clock: idle and maximum session lifetime for guest and signed-in senders; join window expiry and renewal; join ticket single use; purge 7 days after end.
- TURN credential test: issued credential authenticates against the coturn container (`turnutils_uclient` or a Go TURN client), expired credential is refused.

## 5b. iOS test conventions

- `ShareAnywhereCore` is an SPM package with no UIKit dependency: transfer engine (block scheduler, bitmap, hasher, frame codec), clipboard crypto, API client. Its tests run with `swift test` on macOS without a simulator and consume the same vector files as Web and Android (`shared/protocol/schemas/transfer-vectors.json`, `clipboard-vectors.json`).
- XCUITest uses launch arguments `-backendURL`, `-uiTesting`, and `-seedFiles` so the app seeds test documents into its Documents directory on launch; document picker interaction is driven through the Files app UI with accessibility identifiers and falls back to the in-app Documents list when the picker is flaky.
- Guest launch test: fresh install (`-resetState`), assert the Welcome cover then the Transfer tab, with no sign-in sheet presented.
- Guest clipboard test: open the Clipboard tab as a guest, assert the intro and that the pasteboard wrapper recorded zero reads and zero change observations.
- Keep-screen-on test: the `-uiTesting` build exposes `UIApplication.shared.isIdleTimerDisabled` as the accessibility value of a hidden element; assert `true` while waiting for receivers and during a transfer, `false` after completion, pause, cancel, removal, and with the setting off, `false` after pressing Home, and `true` again after returning while the transfer is still active.
- Clipboard foreground capture (signed in, device added): the test sets `UIPasteboard.general.string` via the app's `-uiTesting` hook (simulator shares the host pasteboard; do not rely on host state), activates the app, asserts an event appears; backgrounds the app, changes the pasteboard, asserts no event. `UIPasteControl` is tested by tapping the control; the fallback button test accepts the paste banner if it appears.
- Background suspension: tests use the `-uiTesting` clock injection to shorten the background window and assert a local notification request was scheduled.
- Screenshots are captured with `XCTAttachment` per screen in light/dark and `UIContentSizeCategory.extraExtraExtraLarge`, uploaded as artifacts, and attached to the phase report.
- Nothing in `ios/` is signed in CI; simulator builds use automatic signing disabled (`CODE_SIGNING_ALLOWED=NO`).

## 6. Fixtures

`scripts/gen-fixture.sh <size> <path>` creates a sparse file and writes random 64 KiB blocks at the start, end, and every 97 MiB, then prints the SHA-256. Fixtures are generated in CI, never committed.

## 7. Reporting

Each workflow uploads a JUnit report; `ci.yml` publishes a summary with per-project pass/fail and a link to Playwright HTML reports on failure. Phase reports link to the workflow run that verified each claim.
